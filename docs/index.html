Scheme guide

How to turn an idea for approximate nearest-neighbour (ANN) search on High Bandwidth Flash into a scheme this evaluator can score: what machine you are programming, what ctx is, a scheme written from scratch step by step, and then every argument, field and method explained with examples, costs and pitfalls.

Repository: github.com/envymoon/HBF_ANN_eval. The worked example is docs/tutorial_ivf.py. If anything here disagrees with the code, the code wins; the interface text is TEXT in hbf_eval/contract.py.

Part I · Concepts

1. The machine you program

Your scheme runs on a simulated GPU with two kinds of memory next to it: HBM (fast, small) and HBF (flash stacked like HBM: large, high bandwidth, but each read first has to sense a whole flash page, which takes microseconds). The base vectors do not fit in HBM; they have to live in HBF.

Five facts about HBF shape every design:

  1. A read senses a whole 4 KiB page. Reading 64 bytes or 4096 bytes costs the same sense time (tR, 1.5–20 µs depending on the device). Only the link transfer gets shorter. So put things you need together on the same page.
  2. A bank senses one page at a time. Two reads to pages on the same bank wait for each other; reads to different banks proceed in parallel. There are 32–128 banks per channel. So spread concurrent reads across banks.
  3. Each bank keeps its last 2 pages in buffers. Reading a page that is still in a buffer is a hit: no sense at all. So if several queries need the same page, issue those reads close together.
  4. Every sense costs energy from a fixed power budget. On some devices the budget, not the bank count, limits how many senses per second you get. So fewer senses is better even when banks are idle.
  5. Reads are asynchronous. You issue a read, keep computing, and its data arrives later. A query that needs the result of one read to decide the next (a graph walk) waits a full read time per step.

2. Offline and online

A scheme is three functions. The first two run once, before any query, and are free; the third runs while queries are being served, and is what the score measures.

Why serve cannot see the vectors: on the real machine the vectors are in flash. If serve could read vectors[i] directly, it would get data for free that really costs a flash read. So everything serve needs must be placed by layout and fetched through ctx, which charges the real cost.

3. What ctx is

ctx ("context") is an object the evaluator passes into each of your three functions. You never create it, never store it, and cannot change it. It is your only door to the outside: it tells you about the dataset and the device, gives you your knob values and random numbers, and in serve it is how you read memory, issue flash reads and answer queries. Every ctx call in serve charges simulated time.

Think of it as the API of the machine. A different ctx is passed to each function, with different abilities:

4. How simulated time moves

Nothing in serve is measured with a stopwatch. The evaluator keeps a simulated clock and moves it by rules:

  • A wake starts 1.2 µs after the moment the host woke (the cost of a host round).
  • Each torch operation moves the clock by its billed time (computed from tensor shapes, section 27).
  • Each ctx call moves it by its cost: ctx.hbm waits for the transfer; ctx.submit only hands the reads to the device and returns.
  • Meanwhile the device works on the reads you submitted, in parallel with your code.
  • When serve returns, the host sleeps until something happens (a read completes, a query arrives), then wakes you again.

A query's latency is the clock at ctx.finish minus the clock when it arrived. Throughput is queries per simulated second.

Consequence: a Python loop that would take a second on your laptop may cost almost nothing (if it does no torch work), and one cdist over a huge matrix may cost a lot. What counts is the billed work, not your laptop's speed. The real wall-clock time only matters for the job's time limit (1 h at 100K).

5. Bytes, ids and tensors

  • Everything is a torch tensor. Ids, page numbers, tags and offsets are torch.int64. Pages and read data are torch.uint8 (raw bytes). Vectors and distances are usually torch.float32.
  • Flash holds bytes, not vectors. To store a float32 vector, reinterpret its 4 bytes per value: v.contiguous().view(torch.uint8). To read it back: raw.contiguous().view(torch.float32). The same trick stores an int32 id in 4 bytes.
  • Batch everything. One tensor operation over all open queries costs about the same as one for a single query. Write serve as operations over tensors whose first dimension is "all open queries" or "all completed reads", not as Python loops.
  • Reading a tensor into Python is expensive. int(x), x.item(), x.tolist(), bool(x), if x: on a tensor all cost a host sync (0.5 µs plus the bytes). Use them a few times per wake, not per query.
Part II · Worked example

6. From idea to plan

We will write IVF-Flat from scratch: cluster the vectors with k-means; at query time, find the few clusters nearest to the query and compare the query with every vector in them. It is not the fastest scheme, but it uses every part of the interface. The finished file is docs/tutorial_ivf.py (section 13).

The first design step is to split the idea into "done once" and "done per query", and decide where each piece of data lives:

7. KNOBS

Knobs are the numbers you might want to tune without editing code. Each is name: (default, low, high, scale).

KNOBS = {
    "nlist": (256, 8, 4096, "int"),        # number of clusters
    "kmeans_iters": (8, 1, 30, "int"),     # Lloyd iterations in build
    "nprobe_lo": (2, 1, 256, "int"),       # clusters probed at effort 0
    "nprobe_hi": (32, 1, 1024, "int"),     # clusters probed at effort 1 (--wide opens it to 1024)
}
  • scale is "int" (whole numbers), "linear" or "log" (needs low > 0). It tells tools how to vary the knob; it also rounds "int" knobs.
  • --set nlist=1024 on the command line overrides a default (clamped to [low, high]).
  • A pair x_lo / x_hi is the convention for "the range ctx.effort sweeps": at effort 0 we probe nprobe_lo clusters, at effort 1 nprobe_hi. --wide sets every *_hi knob to its maximum, to check whether a recall level is unreachable or just outside the default range.

8. Writing build

def build(vectors, ctx):
    n = vectors.shape[0]
    K = min(ctx.knobs["nlist"], n)
    cent = vectors[torch.argsort(ctx.uniform(n))[:K]].clone()      # K random vectors as the first centroids
    for it in range(ctx.knobs["kmeans_iters"]):
        assign = nearest(vectors, cent)
        sums = torch.zeros_like(cent).index_add_(0, assign, vectors)
        count = torch.bincount(assign, minlength=K).to(vectors.dtype)
        cent = torch.where(count[:, None] > 0, sums / count.clamp(min=1.)[:, None], cent)
    return {"cent": cent, "assign": nearest(vectors, cent)}
vectors
A float32 tensor of shape [n, D]: 100 000 × 128 for SIFT. SIFT values are whole numbers 0–255 stored as floats.
ctx.knobs["nlist"]
256 by default. It must be a literal string, and the knob must be declared.
ctx.uniform(n)
n random floats. argsort of random numbers is a random permutation: this is how you draw a random sample, since torch.randperm is not allowed (all randomness must come from ctx so runs are repeatable).
Return value
Any dict of tensors. Here cent is float32[256, 128] and assign is int64[100000]. It is cached on disk, so a second run with the same code and knobs skips build.

nearest is a helper we define ourselves: a scheme may have up to 60 top-level functions that call each other by name.

9. Writing layout

layout turns the index into bytes on the device. First decide the record format: what one stored item looks like.

We store the id next to the vector because serve needs to know which vector it just read: it cannot look anything up in index. Records are 64-byte aligned because HBF reads are in units of 64 bytes.

def layout(index, vectors, ctx):
    s = ctx.spec()
    n, K = vectors.shape[0], index["cent"].shape[0]
    size = record_size(s)                     # 192 for SIFT, 448 for DEEP (4 + 384 rounded up)
    per = 4096 // size                        # records per page: 21 for SIFT
    assign = index["assign"]
    order = torch.argsort(assign, stable=True)          # vector ids grouped by cluster
    count = torch.bincount(assign, minlength=K)         # vectors per cluster
    npages = (count + per - 1) // per                   # pages per cluster
    first_page = torch.cumsum(npages, 0) - npages       # first page of each cluster
    first_rec = torch.cumsum(count, 0) - count
    a = assign[order]
    pos = torch.arange(n) - first_rec[a]                # position inside its cluster
    slot = (first_page[a] + pos // per) * per + pos % per   # page * per + slot in page
    P = int(npages.sum())
    body = torch.zeros(P * per, size, dtype=torch.uint8)
    body[:, :4] = 255                                   # id -1 marks an empty slot
    body[slot, :4] = order.to(torch.int32).view(torch.uint8).reshape(n, 4)
    body[slot, 4:4 + s["vector_bytes"]] = pack_rows(vectors[order], s)
    pages = torch.zeros(P, 4096, dtype=torch.uint8)
    pages[:, :per * size] = body.reshape(P, per * size)
    lpage = torch.cat([first_page, first_page[-1:] + npages[-1:]])   # cluster c = pages lpage[c] .. lpage[c+1]-1
    return {"pages": pages, "hbm": {"cent": index["cent"], "lpage": lpage}, "sram": {}, "interleave": 1}
ctx.spec() in layout
Everything build saw (n, dim, k, vector_bytes, dtype, …) plus the device's datasheet (hbm_bytes, tR_us, …, section 15). We only need vector_bytes and dtype here.
"pages"
uint8[P, 4096]: page p on the device holds exactly row p. For SIFT at 100K this is about 5 000 pages (20 MB), well under the HBF capacity.
"hbm"
Two tensors: cent (float32[256, 128], 128 KiB) and lpage (int64[257]). Their total must fit in s["hbm_bytes"]; at 100K SIFT that is at least 640 KB, so we fit. A scheme with bigger tables should check s["hbm_bytes"] and shrink (fewer centroids, fp16) when it does not fit.
"sram"
We use none: {}.
"interleave": 1
Consecutive pages go to consecutive channels, so one cluster's pages spread over all channels and are read in parallel (section 16).

10. Writing serve

serve is called at every wake. It does not handle one query from start to end; it handles whatever happened since the last wake: some reads completed, some new queries arrived. So it is a state machine: the state remembers, for every open query, how far it has got.

Step 1: design the state

One row per open query, as tensors with the same first dimension:

KeyTypeMeaning
qidint64[Q]the query's id (rows kept in increasing qid order)
qfloat32[Q, D]the query vector (we need it when pages come back)
bd, bifloat32[Q, k], int64[Q, k]best k distances and ids so far
leftint64[Q]page reads still in flight; 0 means "done, answer it"

Step 2: design the tag

Every read carries a tag, an integer you choose; the completion comes back with the same tag. The tag must tell you everything you need to process the data. Here: which query, and which page. We encode tag = qid × P + page (P = number of pages), and decode with tag // P and tag % P.

Step 3: the top level

def serve(state, events, ctx):
    s = ctx.spec()
    if "qid" not in state:                       # first wake: state is {}
        state = empty_state(s)
    if events["tags"].shape[0] > 0:              # some reads completed
        state = absorb(state, events, s)
    if events["qids"].shape[0] > 0:              # some queries arrived
        state = start(state, events["qids"], events["queries"], s, ctx)
    return answer(state, ctx)                    # answer what is finished; must return the state dict

Step 4: new queries

def start(state, qids, queries, s, ctx):
    cent = ctx.hbm("cent")                                    # [K, D]: waits for the HBM transfer
    lpage = ctx.hbm("lpage")                                  # [K + 1]
    a, P = qids.shape[0], nprobe(ctx, cent.shape[0])
    lists = torch.topk(torch.cdist(queries, cent), P, dim=1, largest=False).indices   # [a, P] nearest clusters
    first, cnt = lpage[lists].reshape(-1), (lpage[lists + 1] - lpage[lists]).reshape(-1)
    pair = torch.repeat_interleave(torch.arange(a * P), cnt)  # one entry per page to read
    base = torch.cumsum(cnt, 0) - cnt
    pages = first[pair] + torch.arange(pair.shape[0]) - base[pair]
    owner = pair // P                                         # which new query reads it
    size = record_size(s)
    used = ((4096 // size) * size + 63) // 64 * 64            # 4032 for SIFT: skip the unused tail
    ctx.submit(pages, torch.zeros_like(pages), used, qids[owner] * s["pages"] + pages, batch=True)
    ...  # append one state row per new query, with left = number of pages it reads
ctx.hbm("cent")
Fetches the whole tensor from HBM: 128 KiB at 250 GB/s plus 0.1 µs latency ≈ 0.6 µs. Pass rows to fetch only some rows.
nprobe(ctx, K)
Our helper mapping ctx.effort (0 → nprobe_lo, 1 → nprobe_hi). The host runs the whole task at 9+ effort values to draw the recall–throughput curve.
ctx.submit(pages, offsets, nbytes, tags, batch)
One call issues every page read of every new query. offsets are all 0 (start of page), nbytes is one int for all reads, tags as designed, batch=True tells the base die to dispatch them at once rather than wait for its timer. The call returns immediately.

Step 5: completed reads

def absorb(state, events, s):
    size, vb, k = record_size(s), s["vector_bytes"], s["k"]
    per = 4096 // size
    tags = events["tags"]
    row = torch.searchsorted(state["qid"], tags // s["pages"])        # state row of each completion
    rec = events["data"][:, :per * size].reshape(-1, per, size)       # [c, per, size]
    ids = rec[:, :, :4].contiguous().view(torch.int32).squeeze(2).long()   # [c, per]
    vec = unpack_rows(rec[:, :, 4:4 + vb], s)                          # [c, per, D]
    d = ((vec - state["q"][row][:, None, :]) ** 2).sum(2)
    d = torch.where(ids >= 0, d, torch.full_like(d, float("inf")))    # empty slots never win
    ...  # merge the candidates of each row into its best k; left -= completions of that row
events["data"]
uint8[c, 4032]: the bytes of the c completed reads. We cut each page into its 21 records and decode ids and vectors with view.
Merging
Several pages of the same query may complete in one wake, so we lay the candidates out as a [Q, W] matrix (one row per query), concatenate it with bd, and take topk. See the full listing.

Step 6: answer finished queries

def answer(state, ctx):
    done = state["left"] == 0
    if not bool(done.any()):                     # one host sync per wake: fine
        return state
    ctx.finish(state["qid"][done], state["bi"][done])
    keep = ~done
    return {key: v[keep] for key, v in state.items()}

ctx.finish takes the query ids and an int64[a, 10] tensor of result ids. Each answered client immediately sends its next query, which arrives in the next wake's events["qids"].

11. One query's life

A single query on device C at 100K (tR = 4 µs), with numbers rounded:

Simulated timeWhat happens
100.0 µsThe previous query of this client was answered; this query arrives.
100.0 → 101.2The host wakes the GPU (1.2 µs per wake). serve sees it in events["qids"].
101.2 → 101.8ctx.hbm("cent"): 128 KiB from HBM.
101.8 → 101.9cdist, topk, index arithmetic: billed from shapes, small for one query.
101.9ctx.submit: say 16 probed clusters × 19 pages ≈ 300 reads go to the device. serve returns.
≈ 106The first pages are sensed (4 µs) and transferred; the host wakes serve with those completions.
106 → ≈ 130The remaining reads complete bank by bank: about 300 reads over 4 channels × 64 banks, plus link time. Every wake folds the arrived pages into bd, bi and decrements left.
≈ 130left hits 0; answer calls ctx.finish. Latency ≈ 30 µs. The client sends its next query.

With many clients, many queries are in flight at once and each wake handles completions of all of them together.

13. Full listing

The complete scheme, docs/tutorial_ivf.py. It passes bench check; its build and layout output have been decoded back to the original ids and vectors.

"""Tutorial scheme: IVF-Flat on HBF. k-means clusters; each cluster's full vectors packed into its own run of HBF pages;
centroids and the page range of every cluster in HBM. A query reads every page of its nprobe nearest clusters and keeps
the k nearest records it sees. Written to be read alongside the manual (docs/index.html), not to be fast."""

KNOBS = {
    "nlist": (256, 8, 4096, "int"),        # number of clusters
    "kmeans_iters": (8, 1, 30, "int"),     # Lloyd iterations in build
    "nprobe_lo": (2, 1, 256, "int"),       # clusters probed at effort 0
    "nprobe_hi": (32, 1, 1024, "int"),     # clusters probed at effort 1 (--wide opens it to 1024)
}


# ---------------------------------------------------------------- build: offline, not timed
def build(vectors, ctx):
    n = vectors.shape[0]
    K = min(ctx.knobs["nlist"], n)
    cent = vectors[torch.argsort(ctx.uniform(n))[:K]].clone()      # K random vectors as the first centroids
    for it in range(ctx.knobs["kmeans_iters"]):
        assign = nearest(vectors, cent)
        sums = torch.zeros_like(cent).index_add_(0, assign, vectors)
        count = torch.bincount(assign, minlength=K).to(vectors.dtype)
        cent = torch.where(count[:, None] > 0, sums / count.clamp(min=1.)[:, None], cent)
    return {"cent": cent, "assign": nearest(vectors, cent)}


# Index of the nearest row of c for every row of x, in chunks of 8192 rows to bound memory.
def nearest(x, c):
    cc = (c * c).sum(1)
    out = []
    for i in range(0, x.shape[0], 8192):
        out.append(torch.argmin(cc[None, :] - 2. * x[i:i + 8192] @ c.T, dim=1))
    return torch.cat(out)


# ---------------------------------------------------------------- layout: offline, not timed
def layout(index, vectors, ctx):
    s = ctx.spec()
    n, K = vectors.shape[0], index["cent"].shape[0]
    size = record_size(s)                     # bytes of one record: 4-byte id + the vector, rounded up to 64
    per = 4096 // size                        # records per page
    assign = index["assign"]
    order = torch.argsort(assign, stable=True)          # vector ids grouped by cluster
    count = torch.bincount(assign, minlength=K)         # vectors per cluster
    npages = (count + per - 1) // per                   # pages per cluster (each cluster starts on a fresh page)
    first_page = torch.cumsum(npages, 0) - npages       # first page of each cluster
    first_rec = torch.cumsum(count, 0) - count          # first position of each cluster in `order`
    a = assign[order]
    pos = torch.arange(n) - first_rec[a]                # position of each vector inside its cluster
    slot = (first_page[a] + pos // per) * per + pos % per   # global record slot = page * per + slot in page
    P = int(npages.sum())
    body = torch.zeros(P * per, size, dtype=torch.uint8)
    body[:, :4] = 255                                   # id -1 (four 0xFF bytes) marks an empty slot
    body[slot, :4] = order.to(torch.int32).view(torch.uint8).reshape(n, 4)
    body[slot, 4:4 + s["vector_bytes"]] = pack_rows(vectors[order], s)
    pages = torch.zeros(P, 4096, dtype=torch.uint8)
    pages[:, :per * size] = body.reshape(P, per * size)
    lpage = torch.cat([first_page, first_page[-1:] + npages[-1:]])   # cluster c = pages lpage[c] .. lpage[c+1]-1
    return {"pages": pages, "hbm": {"cent": index["cent"], "lpage": lpage}, "sram": {}, "interleave": 1}


def record_size(s):
    return ((4 + s["vector_bytes"] + 63) // 64) * 64


# Vectors to their stored bytes: uint8 data one byte per value, float32 four.
def pack_rows(v, s):
    if s["dtype"] == "uint8":
        return v.round().clamp(0, 255).to(torch.uint8)
    return v.contiguous().view(torch.uint8)


def unpack_rows(raw, s):
    if s["dtype"] == "uint8":
        return raw.float()
    return raw.contiguous().view(torch.float32)


# ---------------------------------------------------------------- serve: online, timed
def serve(state, events, ctx):
    s = ctx.spec()
    if "qid" not in state:
        state = empty_state(s)
    if events["tags"].shape[0] > 0:
        state = absorb(state, events, s)
    if events["qids"].shape[0] > 0:
        state = start(state, events["qids"], events["queries"], s, ctx)
    return answer(state, ctx)


# One row per open query, rows kept in qid order (qids arrive in increasing order and rows are only appended or removed).
def empty_state(s):
    k = s["k"]
    return {"qid": torch.zeros(0, dtype=torch.int64),          # query id
            "q": torch.zeros(0, s["dim"]),                     # query vector
            "bd": torch.zeros(0, k),                           # best distances so far
            "bi": torch.zeros(0, k, dtype=torch.int64),        # their ids
            "left": torch.zeros(0, dtype=torch.int64)}         # page reads still in flight


def nprobe(ctx, K):
    lo, hi = ctx.knobs["nprobe_lo"], ctx.knobs["nprobe_hi"]
    return max(1, min(K, int(round(lo + ctx.effort * (hi - lo)))))


# New queries: nearest clusters from the HBM centroids, then one read per page of those clusters.
def start(state, qids, queries, s, ctx):
    cent = ctx.hbm("cent")                                    # [K, D]: waits for the HBM transfer
    lpage = ctx.hbm("lpage")                                  # [K + 1]
    a, P = qids.shape[0], nprobe(ctx, cent.shape[0])
    lists = torch.topk(torch.cdist(queries, cent), P, dim=1, largest=False).indices   # [a, P]
    first, cnt = lpage[lists].reshape(-1), (lpage[lists + 1] - lpage[lists]).reshape(-1)
    pair = torch.repeat_interleave(torch.arange(a * P), cnt)  # one entry per page to read
    base = torch.cumsum(cnt, 0) - cnt
    pages = first[pair] + torch.arange(pair.shape[0]) - base[pair]
    owner = pair // P                                         # row of the new query that reads it
    size = record_size(s)
    used = ((4096 // size) * size + 63) // 64 * 64            # bytes of a page that hold records
    ctx.submit(pages, torch.zeros_like(pages), used, qids[owner] * s["pages"] + pages, batch=True)
    k = s["k"]
    new = {"qid": qids, "q": queries, "bd": torch.full((a, k), float("inf")),
           "bi": torch.zeros(a, k, dtype=torch.int64), "left": torch.bincount(owner, minlength=a)}
    return {key: torch.cat([state[key], new[key]]) for key in state}


# Completed reads: decode the tag, compute exact distances of every record on the page, merge into each query's k best.
def absorb(state, events, s):
    size, vb, k = record_size(s), s["vector_bytes"], s["k"]
    per = 4096 // size
    tags = events["tags"]
    row = torch.searchsorted(state["qid"], tags // s["pages"])        # which state row each completion belongs to
    rec = events["data"][:, :per * size].reshape(-1, per, size)       # [c, per, size]
    ids = rec[:, :, :4].contiguous().view(torch.int32).squeeze(2).long()   # [c, per]
    vec = unpack_rows(rec[:, :, 4:4 + vb], s)                          # [c, per, D]
    d = ((vec - state["q"][row][:, None, :]) ** 2).sum(2)
    d = torch.where(ids >= 0, d, torch.full_like(d, float("inf")))
    crow = row[:, None].expand(-1, per).reshape(-1)
    order = torch.argsort(crow, stable=True)
    rs = crow[order]
    col = torch.arange(rs.shape[0]) - torch.searchsorted(rs, rs)      # position of each candidate within its row
    Q, W = state["qid"].shape[0], int(col.max()) + 1
    cd = torch.full((Q, W), float("inf"))
    ci = torch.zeros(Q, W, dtype=torch.int64)
    cd[rs, col] = d.reshape(-1)[order]
    ci[rs, col] = ids.reshape(-1)[order].clamp(min=0)
    alld, alli = torch.cat([state["bd"], cd], 1), torch.cat([state["bi"], ci], 1)
    top = torch.topk(alld, k, dim=1, largest=False).indices
    return dict(state, bd=torch.gather(alld, 1, top), bi=torch.gather(alli, 1, top),
                left=state["left"] - torch.bincount(row, minlength=Q))


# Answer every query whose reads are all in, and drop its row.
def answer(state, ctx):
    done = state["left"] == 0
    if not bool(done.any()):
        return state
    ctx.finish(state["qid"][done], state["bi"][done])
    keep = ~done
    return {key: v[keep] for key, v in state.items()}

16. The plan

{"pages": uint8[P, 4096], "hbm": {str: tensor}, "sram": {str: tensor}, "interleave": int, "refresh": "default" | "scheme"}
"pages"
uint8[P, 4096], P ≥ 1. Row p is page p on the device, byte for byte. Content is up to you: records, adjacency lists, codes, anything. P ≤ (8 − m) × hbf_pages_per_position.
"hbm"
Named tensors of any dtype and shape. The first dimension is the row that ctx.hbm(name, rows) indexes. Total bytes ≤ hbm_bytes. To reserve space you fill later in serve, put a zero tensor of the size you need.
"sram"
Named tensors placed in the base-die SRAM. Row r is on channel r mod C. Per channel, the bytes of the rows it holds must fit sram_bytes_per_channel. Reading it costs the channel link, not HBM. Use {} if sram_bytes_per_channel is 0.
"interleave"
g, 1 to 220: runs of g consecutive pages go to one channel, then the next. Placement: 
channel = (p // g) % C
local   = g * (p // (g * C)) + p % g      # index of the page within its channel
die     = (local // banks_per_die) % dies_per_channel
bank    = local % banks_per_die
Example, C = 4 channels, 64 banks:
page012345…
g = 1: (channel, bank)(0, 0)(1, 0)(2, 0)(3, 0)(0, 1)(1, 1)spread over channels
g = 4: (channel, bank)(0, 0)(0, 1)(0, 2)(0, 3)(1, 0)(1, 1)runs stay on a channel
Use g = 1 to read consecutive pages in parallel over all channels; use a larger g to keep related pages on one channel. Since placement is a fixed formula, you can put any page on any bank by choosing its page number.
"refresh" (optional)
"default": the host pays flash refresh automatically when a die is idle, or at once when a plane owes more than refresh_slack_pages. "scheme": refresh is paid only when you call ctx.refresh (section 24); the device still forces it above 2 × refresh_slack_pages.

No other keys are allowed. Writing the pages is free (no program time or wear for loading the index).

17. serve(state, events, ctx): state and events

def serve(state, events, ctx) -> state

state

  • Whatever you returned last time; {} at the first call of each run (each task × effort level is a new run).
  • Must be a dict. Values may be tensors, numbers, strings up to 64 characters, lists, tuples and dicts with string keys, nested at most 8 levels.
  • Size cap ctx.spec()["state_bytes"] = min(clients × 64 KiB, 16 MiB at 100K / 32 MiB at 1M). It models what fits on chip, so it cannot hold the dataset; keep only per-query progress.

  • Cost to you: no clock time; the device works in the background.
  • What the device does: each read senses its whole page (unless the page is in one of its bank's 2 buffers), then sends the requested bytes over the link. Reads reach a bank in the order you submit them.
  • Partial reads save link time, not sense time. They pay off when the link is the bottleneck (fast tR, slow link).
  • Limits: 220 reads per call, 221 in flight. Beyond mocs per channel, reads wait on the host side.
  • Batch or not: use batch=True when you issue a group at once; without it, a lone read can wait up to the timer (0–2 µs).
  • Pitfall: all four arguments must be int64 tensors of one length (torch.tensor([...]) gives int64 for Python ints). An offset that is not a multiple of 64, or a read crossing the page end, fails the run.

Choose when the next wake happens: when at least count events (completions plus arrivals) are waiting, or timeout_us has passed, or nothing is in flight. Applies to the next wake only; the default is "wake on the first event". Fewer wakes save 1.2 µs each and let you batch more work, at the price of some latency (section 25).

for i in ctx.lanes(n):

A loop whose body runs once per lane, all lanes in parallel on the GPU. Inside a lane, turning a tensor into a Python value (if x[i] > y:, int(...), .item()) costs 0.02 µs instead of a 0.5 µs host sync. Use it for per-query control flow (section 22).

  • n: an int, 0 to 65 536, usually the number of open queries.
  • Cost: 0.6 µs + max(sum of all lanes' compute, max over lanes of (24 × its compute + its branches + its HBM/SRAM waits)). A lane runs at one SM's speed (1/24 of the GPU); all lanes together never beat the whole GPU.
  • ctx.submit and ctx.finish inside a lane take effect at that lane's own time when the loop ends.
  • Rules: no break or return inside the loop; no nesting; no ctx.debt / ctx.refresh inside.

Every sense slowly disturbs its flash block; the device must eventually spend time rewriting pages ("refresh"). ctx.debt() gives the pages of refresh each die owes (die id = channel × dies_per_channel + die). ctx.refresh(dies, counts) starts that many refresh operations on those dies (int64 tensors; counts may be one int). One operation waits for the die's reads in progress, then holds the die for tR + program time. Only meaningful with plan["refresh"] = "scheme"; see section 24. Not allowed inside a lane.

Part IV · Patterns

How common ideas map onto the interface. These are fragments; the bundled schemes in hbf_eval/schemes/ are full examples.

19. A graph walk (dependent reads)

Each node's record (vector + neighbour ids) is on HBF. A query keeps a candidate list; each step reads the best unvisited node, and the next step can only start when that read returns. In serve this is a loop across wakes, not inside one:

# state per query: cand_ids [Q, L], cand_d [Q, L], visited bitmap or list, inflight [Q]
# 1. completions: decode each node's neighbours, compute their distances (from HBM codes or the vectors you read),
#    merge into cand_*, mark the node visited, inflight -= 1
# 2. for every query with inflight == 0: pick its best unvisited candidates (beam width W from ctx.effort)
#    and submit their records in ONE ctx.submit for all queries (tag = qid * n + node)
# 3. queries with no unvisited candidate left: ctx.finish

Latency is about (number of hops) × (one read). The usual ways to shorten it: fewer hops (better entry points from an HBM table, see compass.py), more useful nodes per read (put neighbours on the same page: pageann.py, starling.py), or not waiting for the slowest read of a step (pipeann.py).

20. Coalescing reads by unit

When many queries read the same pages, issue them so that reads of one page reach its bank back to back: the second one hits the page buffer and costs no sense.

m = ctx.mapping(pages)                                         # [r, 3]: channel, die, bank
unit = (m[:, 0] * s["dies_per_channel"] + m[:, 1]) * s["banks_per_die"] + m[:, 2]
order = torch.argsort(unit * s["pages"] + pages, stable=True)  # by unit, then by page
ctx.submit(pages[order], offsets[order], nbytes, tags[order], batch=True)

Check the effect in diag.hit_rate and diag.senses_per_query.

21. Pipelining and speculation

Because submit does not wait, you can issue the next reads before the current ones return: read the next probe's pages while still scanning this one, or read the second-best candidate's record in case the best one disappoints. Speculative reads cost senses (power, bank time) even when unused, so check senses_per_query against the latency you gain.

22. Per-query branches with lanes

Outside a lane, any decision on a tensor value is a host sync; a loop over 500 queries with an if costs 500 × 0.5 µs. Inside ctx.lanes the same branch costs 0.02 µs and the queries run in parallel:

Q = state["qid"].shape[0]
for i in ctx.lanes(Q):
    if float(state["gap"][i]) < 0.01:                        # this query has converged: stop early
        ctx.finish(state["qid"][i:i + 1], state["bi"][i:i + 1])
    else:
        nxt = state["cand"][i, :int(state["width"][i])]       # its own beam width
        ctx.submit(page_of(nxt), off_of(nxt), 192, state["qid"][i] * s["n"] + nxt)

Heavy arithmetic (distances over many vectors) is still cheaper as one batched op outside the loop: inside a lane it runs at 1/24 of the GPU.

23. A cache filled while serving

Reserve space in layout, fill it in serve:

# layout: 512 cached pages and a table of which page each slot holds (-1 = empty); check it fits s["hbm_bytes"]
hbm["cpage"] = torch.full((512,), -1, dtype=torch.int64)
hbm["cdata"] = torch.zeros(512, 4096, dtype=torch.uint8)

# serve: look up before reading from flash
cp = ctx.hbm("cpage")                                    # 4 KiB
hit = (pages[:, None] == cp[None, :])                    # [r, 512]
slot = hit.float().argmax(1)
is_hit = hit.any(1)
data_hit = ctx.hbm("cdata", slot[is_hit])                # served from HBM, no flash read
# ... submit the misses; when a hot page comes back, store it:
ctx.hbm_write("cdata", victim_slots, new_pages)          # victim_slots distinct int64[r], new_pages uint8[r, 4096]
ctx.hbm_write("cpage", victim_slots, new_page_ids)

24. Your own refresh policy

# layout:  return {..., "refresh": "scheme"}
# serve: pay refresh when the device is quiet
d = ctx.debt()                                           # float64[dies]
owe = torch.nonzero(d >= 1).flatten()
if owe.numel() > 0 and ctx.pending().numel() < 16:     # few reads in flight
    ctx.refresh(owe, 1)

If you never pay, debt grows until reads start retrying, and above 2 × refresh_slack_pages the device forces payment at a moment you did not choose.

25. Fewer, fuller wakes

By default serve wakes on every completion. With hundreds of reads in flight that means hundreds of wakes, each costing 1.2 µs plus your fixed per-wake work. Ask to wake when more is ready:

ctx.wait(count=32, timeout_us=2 * s["tR_us"])     # wake when 32 events wait, or after two sense times

The timeout bounds the delay at low load, where 32 events may never come.

28. The device's read path

  1. The read arrives at its channel's base die; beyond mocs reads in flight it waits on the host side.
  2. A normal read is held until the base-die timer fires (0–2 µs); a Batch Read dispatches the held reads and itself at once.
  3. At its bank: if the page is in one of the 2 page buffers, it is a hit (go to 6).
  4. Otherwise it queues at the bank (strict order). At its turn, a page loaded by an earlier sense also hits; else it takes a buffer, draws sense energy from the stack's power budget (waits if the budget is short; the budget can burst up to 10 × tR of power), and senses for tR.
  5. The 4 KiB page moves to the base die over the die's core-die channel; the bank senses nothing else meanwhile.
  6. The requested bytes cross the channel link, one transfer at a time.
  7. The completion shows up in events at the next wake.

Every sense adds refresh debt; debt above refresh_slack_pages makes senses retry sometimes. HBM has its own links.

29. Language rules

  • Module level: one docstring, one KNOBS literal, top-level defs. Nothing else. No imports: torch, F (torch.nn.functional) and math are already there.
  • Builtins: abs min max range len float int bool enumerate zip sum any all isinstance tuple list dict round sorted reversed pow map filter.
  • torch: tensor functions, creation functions, dtypes, torch.linalg, torch.special, torch.fft, torch.autograd.grad, torch.no_grad.
  • Not allowed: import, class, try/raise, global, yield, async, del, decorators, match; names starting with _; assigning attributes; mutable default arguments; torch.nn, torch.optim, torch.cuda, file IO, global randomness (rand, randperm, …), empty, numpy.
  • Easy to trip on: a local variable may not reuse the name of a builtin (sum, max, list, …) or of one of your own functions; knobs are read only as ctx.knobs["literal"].
  • Size: ≤ 60 functions, ≤ 80 lines each, ≤ 160 000 characters.

  • Per task: log2(your throughput at recall@10 = 0.90 ÷ batched brute force's on the same device). 0 = as fast as the scan, +1 = twice as fast.
  • An operating point counts only if its worst 5% of queries average recall ≥ 0.3.
  • If raising the effort makes the reads in flight overflow the evaluator's cap (221 outstanding reads), the sweep stops there: the points measured below that effort still count, a recall level not yet reached scores as not reached, and the task record carries capped_at (the effort that overflowed).
  • Never reaching 0.90 scores between −16 and −8, by how close you get.
  • The score is the mean over the four tasks; 0.95 and 0.99 are reported too. Build time, index size and the diagnostics are reported, not scored.
